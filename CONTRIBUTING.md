# Contribution Guidelines

Welcome! Thank you for considering adding to this project.

This document explains the best way to go about it.
These aren't strict rules, they're guidelines.

## Step 1: What needs fixing?

While "I want to help, tell me what to do" is a good attitude, remember this
is my hobby.  I can't really manage who gets assigned what task, based on their
skills and experience.  I need you to make that call.

If you have a specific idea for a new feature, or modification of an existing
one, then you're on the right track.

Do you have *lots* of ideas?  Please make each one be a separate change.
Lots of small focused pull requests work better than a few sprawling ones.


## Step 2: Contact me first

Before you get too deep into your contribution, please contact me and tell
me what you plan to do.  There's always a chance that somebody else is already
working on the same thing.  You might want to collaborate, or just wait while
they do the work.

My email address is [kirkenda@gmail.com](mailto:kirkenda@gmail.com).

There's also a chance that your idea for where "edj" should go is fundamentally
different from where I think it should go.  If that happens, your proposed
change will never be part of my "edj"... but if you really want to follow your
vision then feel free to start your own independent branch.  Open source is
great that way.  And by contacting me first, at least you know what you're
in for.


## Step 3: Branch!

After downloading the code from github, compile it to make sure it works
on your system.  Then create a new git branch for your work.  Have fun coding!

If you have questions while coding, please ask me!  I want to enable you
any way I can.  Also, the questions you ask are probably the same questions
that other people *should* be asking.  I need to know that.  Maybe I'll add
an article about it, or edit the documentation.

Make sure the code you contribute is *your* code.  Don't copy and paste
code that you didn't code yourself specifically for "edj".  Don't even
copy from another open source project, unless it also uses the same license.
And tell me if you do copy code.

Extensive use of AI code generation counts as "copy and paste".  Using AI
for code review is great, but don't let it write too much of the code
because you need to understand it.

After coding: test it, analyze it, clean it up, document it, and push it.
And create a pull request.

There's a decent chance I'll come back to you with questions.  I might
request that you make some changes.


## Step 4: Maintain it forever

If I'm hesitant to accept a change that you're offering, this is probably why.
Somebody is going to have to maintain your code.  Hopefully you.  But if not
you then me, and that can become a burden.

This shouldn't scare you.  It's just something to keep in the back of your
mind: "Will I have time to maintain this?"
