After 1.0

2026-04-06

Some features have been more-or-less designed but not yet implemented.
There are a number of potential features that I've explored and in some cases even designed and even done some coding on, but are not implemented in version 1.0. These are all useful things, but aren't so critical that I had to delay release version 1.0 just to add them.

Obviously this isn't an exhaustive list. The next version of jx will include features not listed here, I'm sure.

Screen

The existing command line interface is nice. The interactive read-evaluate-print-loop is very nice. But I want a full-screen terminal-based user interface, implemented as a "-lscreen" plugin.

This would add the ability to open up panels/windows/tabs for a variety of purposes:

  • Browsing JSON data, with expand/contract, click-to-copy-expression, click-to-copy-value, editable value, and a search feature.
  • Using the diff() or find() output as a clickable index.
  • Accessing the documentation, with clickable links and click-to-copy examples.

The "fineline" line input library was designed to work well in applications that use the -lncursesw library, which the "screen" plugin will undoubtedly use. You won't lose any line-editing functionality by using the "screen" plugin.

Data Types

Currently, jx allows you to declare types for vars, consts, functions, and function arguments, but it ignores those declarations. They're currently useful only as comments.

The benefits of truly parsing data types are:

  • It'll catch errors in scripts, hopefully making them more reliable.
  • The case keyword can be modified to accept a type declaration instead of a single literal. Since literals are valid type declarations, this won't break any scripts. It will, however, add the ability to use a "|"-delimited list of values, or even a complex data type as a case.
  • The IS NULL and IS NOT NULL operators will be replaced with generic IS type and IS NOT type operators. Since null is a valid type specifier, this won't break existing code.

As in TypeScript, specifying data types will be entirely optional. For quick-and-dirty scripts that you compose while debugging, you'll probably want to skip type specifications and checking.

The current type parser is mostly there as a place holder for the "real" type parser.

Registry of Global Vars/Consts

Currently, when you declare a global var or const, it simply adds the key and initial value to the global.vars or global.consts objects. This change will add an internal registry of global vars and consts.

The registry will store the filename and line number where the var/const was declared. If some other file tries to redeclare it then that's an error. When you load multiple script files, this will prevent them from interfering with each other. However, if you reload a script (after editing it, presumably) then it will be allowed to redeclare its own vars/consts.

The registry can also store the declared type of vars/consts, and use that to detect errors.

Also, I expect to add support for asynchronous events at some point (see below) and that will require data locks for global vars. The registry gives me a place to store those locks. None of the built-in functions alter variables, but you can write functions in jx script that do.

There is already a global registry of functions, by the way. This is subtly different from the var/const registry, in that functions are shared across contexts, but global vars/consts are tied to a specific context.

Pre-Command Hook

I have plans for a hook that will allow a C function to be called before each script command is executed. Some of the things this could be used for are:
  • Tracing execution. Probably this would be implemented in the log plugin, and would act sort of like automatically-generated log commands. You could control where the trace information is sent, that way.
  • Debugging. This would be a new plugin, and it would allow you to set breakpoints, single-step, examine data... all the delightful things you expect from a debugger. It's likely to depend on the planned "screen" plugin.
  • Detecting asynchronous events, such as the completion of an HTTP request that was running in the background.

Asynchronous Events

Sometimes you want to do things like start multiple HTTP requests in the background and react when they finish. Not only does it make scripts run faster, but it also offers new ways to design scripts.

The Pre-Command Hook (previous section) will play a big role in this. It gives us a way to have the main task to detect when some other task completes.

JavaScript's syntax for handling things like this won't work in jx, because JavaScript's implementation depends on object classes and closures (basically function pointers) which jx doesn't support.

This is separate from using multiple CPU cores, by the way. JavaScript is single-threaded but still supports asynchronous events. Both are nice, and there is some overlap in design requirements, so maybe I'll support the use of multiple CPU cores. (I'm trying to avoid the term "multithreading" here, because people tend to assume multiple threads equals multiple cores, but that isn't always the case.)

I chose to make jx run as a single thread because I often run it on live web hosts, and I don't want my scripts to tie up all of the CPU cores. As long as 7 out of 8 cores are still serving up the web app, it'll run fast enough. If jx ever supports the use of multiple CPU cores, it will need a way to limit the number of cores used.

POSIX plugin

This would add support for some low-level things such as reading directories and files, and opening network connections. These are huge security holes, but there are legitimate uses for this too. Sometimes you just need to chown() a file.

POSIX is huge, so honestly this will probably only ever be subset of it. A useful subset.

I've deliberately avoided giving any jx scripting functions the same name as a POSIX function, just to keep this potential alive.

Key Registry

Currently, member keys (and all names really) are stored as text. When you look up a member, the search compares member names as strings. This is rather slow! The alternative is to create a registry that maps name strings to integers, and then search by comparing those integers.

This could also improve name completion, since the registry would contain every known name. I'd still want it to be context-aware, but as a desperation move it could still look across all names when trying for a completion.

Template Strings

Template strings are a JavaScript feature that lets you embed expressions within plain text. Clearly something like that could be useful when generating reports or converting data to specific text format.

They are enclosed in backtick (`) characters, which jx (and SQL) uses for quoting keys/names that contain problematic characters. I don't think this will be a problem; if a backtick-quoted string contains "${expr}" then it's a template string; otherwise its a quoted key/name.

This is decided at compile time, not run time. If a backtick-quoted string is a template, then it gets converted to a function call, with the embedded expressions used as arguments to that function.

JavaScript allows you to optionally put a magic word before the template string to use a different parser. I might support that, because it'd offer a way for SQL query arguments to be automatically quoted.

XML Templates

The XML plugin already has an XML serializer that reverses the effect of its parser, allowing you to rewrite XML that you've previously read. That doesn't help when you're trying to generate a new XML document, such as a request to a SOAP server. XML tends to be very picky about formats, so there's a good chance you'll need to painstakingly construct the string.

I plan to add a template-driven XML serializer. This is much more complex than JavaScript template strings. It'll have the ability to loop over arrays, and to eliminate tags or attributes for which no data is available.

The next step would probably be a utility that converts a WSDL specification into a set of XML templates.

Complex Blobs

Blobs are compact arrays of bytes. The blob() function can convert that to text, but most binary data contains a mixture of structs. It would be nice if we could convert those structs into objects, or arrays of objects. I envision extending blob() to allow you to pass an offset, length, and/or a string specifying the layout of an object.

All of the constants currently defined in the Blob object are negative, so they won't clash with offset or length numbers.

Data Compression, and Support for Non-UTF-8 Text

These are obviously useful, but surprisingly hard to implement. Normally, jx just maps a JSON file into memory and parses it with the assumption that it contains UTF-8 text. If the file is compressed, then we need to generate an uncompressed version of the file that we can map into memory. If it isn't UTF-8 then we need to run it through a recode utility.

We also need to remember what transformations we apply to the original file to make it parsable, so that when we rewrite the data out to the file, we can reverse the changes. If it started as gzipped Shift-JIS, then it should be rewritten as gzipped Shift-JIS.
