How Deferred Arrays Are Implemented

2025-09-20

This article is for people who want to implement a new type of deferred array, or simply use potentially-deferred arrays in their C code. Deferred arrays are like normal arrays in many ways, and there are library functions for handling arrays in general which hide most of added complexity for typical use. Case studies of specific types of deferred arrays are presented.
Deferred arrays are arrays whose elements don't all reside in memory at the same time. They offer a way to process extremely large JSON files, or in some special cases where large data could be generated from smaller data such as a 1 ... 1000000 integer array generator.

This article describes the challenges to implementing deferred arrays, and the solutions used.

Most people can ignore this, since deferred arrays are intended to act as much like normal in-memory arrays as possible. The information here might be useful if you're implementing a plugin to access a database, and want tables to be represented by deferred arrays.

"Normal" Arrays

Non-deferred arrays are represented by linked lists of edj_t nodes. There's a edj_t with ->type=EDJ_ARRAY, and its ->first points to the first element. To step from one element to the next, follow the element's ->next pointer. To iterate over a non-deferred array, you can... 
		
	/* This only works for non-deferred arrays! */
	edj_t *array = edj_parse("[1,true,\"hello\"]");
	edj_t *element;
	for (element = array->first; element; element = element->next) {
	    /* do something with element here */
	}

Quick and easy! We want something similar for deferred arrays.

The Basics of Deferred Arrays

Deferred arrays are also represented by a edj_t with ->type=EDJ_ARRAY, but instead of having ->first point to the edj_t of the first element, it points to a EDJ_DEFER. In other words, for any deferred array, its ->first->type=EDJ_DEFER.

Internally, though, there's some funny business going on. Instead of pointing to a real edj_t, it actually points to a edjdef_t. edjdef_t is a struct which starts in which the first member is a edj_t, but there are other members tacked on too. There's a fns member which points to a collection of function pointers that implement this particular deferred array's behavior, and a file member which points to the file that deferred data is being read from (if any). If a other storage is needed, then yet another layer of type-spoofing may be present to add that storage.

Still, since it starts with edj_t data, the ->type field is valid, and will always be EDJ_DEFER.

The collection of function pointers includes one for finding the first element, or for the next element, and possibly some others for optimizing things like finding the n'th element.

edj_is_deferred_array() and edj_is_deferred_element()

If a non-deferred array happens to be empty then the above test would be dangerous since it'd involve dereferencing NULL. The edj_is_deferred_array() function does the test in a safe way. It's also less cryptic. However, the design of deferred arrays is intended to allow the same code to work on normal and deferred arrays with (almost) equal ease, so you rarely need to know this.

Similarly, edj_is_deferred_element() tests whether an element was read from a deferred array. This can be significant because when you step from one element to the next, then the old element is freed. If you need to save an element's value, or even just part of its value, then you need to copy it using edj_copy().

edj_first() and edj_next()

The edj_first(array) and edj_next(element) functions are used for iterating over the elements of an array. They work for both "normal" and deferred arrays. For "normal" arrays they use array->first and element->next, just like the above loop.

But for deferred arrays, edj_first() invokes the deferred array's function for finding the first element (which could return NULL if the deferred array turns out to be empty). The first element's ->next pointer will point to a copy of the array's ->first data describing the deferred array, to facilitate stepping to the next element, along with any other data necessary for scanning the array.

Similarly, for elements from a deferred array, the edj_next() function will invoke the array's function for finding the next element. It frees the old element, reuses the edjdef_t data as the next element's ->next pointer value. If there is no next element, then it will free the edjdef_t and any other resources involved in the scan, and return NULL.

This means no extra cleanup is required if your loop always continues until edj_next() returns NULL. 

		
	/* This works for any array */
	edj_t *array = edj_parse("[1,true,\"hello\"]");
	edj_t *element;
	for (element = edj_first(array; element; element = edj_next(element)) {
	    /* do something with element here */
	}

One big "gotcha!" is that since edj_next() frees the current element before moving onto the next, you can't save a pointer to it, or any other edj_t node within the element. If you need to save an element, or part of an element, that is scanned this way then you need to make a copy of it via edj_copy(). You can use the edj_is_deferred_element() function to decide whether copying is necessary... or just always copy.

Another thing to watch out for is that if you have nested arrays and the outer is deferred but the inner one isn't, then applying edj_is_deferred_element() on the inner array's element will return false, but when edj_next() is called on the outer array's element, then inner element will be automatically freed because it was part of the outer element.

edj_break()

If your array scanning loop exits before edj_next() returns NULL, then you need to call edj_break() to free the last element and all data that was allocated to support the scan.

For simplicity's sake, you can call edj_break() with an element that didn't come from a deferred array, or for a NULL pointer, in which case it does nothing. You can safely call edj_break() after breaking out of any array-scanning loop.

Effects on edj_by_index(), edj_by_key_value(), and edj_by_expr()

You need to call edj_break() on the value returned by any of these functions.

The edj_by_index() and edj_by_key_value() functions use edj_first()/edj_next() to loop over the array, and return the requested element. This is exactly the kind of thing that edj_break() is meant to clean up for deferred arrays.

The situation with edj_by_expr() is more complex. It can involve finding an element of an array, and that array could be deferred, but the returned value isn't necessarily the whole element. For example... 

	edj_t *result = edj_by_expr(data, "address[0].zipcode", NULL);
... will look for "address" in data, element 0 from the address array, and then "zipcode" in that element. If "address" is a deferred array then "address[0]" will be a deferred element but "address[0].zipcode" is not. So edj_by_expr() shuffles things around to make "address[0].zipcode" look like an element of that same deferred array. Kind of wacky, but necessary to avoid leaking the memory used to keep track of that deferred array scan.

Effects on edj_length() and edj_is_table()

The edj_length() and edj_is_table() functions work for both normal and deferred arrays.

The array->text member is abused for the sake of efficiency. Instead of requiring an array to be scanned completely to determine its length, or whether it is a table, that data is rammed into the array->text field. This is true for both normal and deferred arrays, but it is especially helpful for deferred arrays because scanning them could involve a lot or parsing or I/O.

The array->text[1] character is used to store a table flag. This is 't' if the array is a table, 'n' if it is not a table, or anything else (usually '\0') if unknown. For unknown, we do still need to scan the whole array.

The length is stored in array->text[2] through [5]. There's a EDJ_ARRAY_LENGTH(array) macro for accessing those four bytes as an unsigned integer. If the length is unknown then EDJ_ARRAY_LENGTH(array) will be 0. If the length of a normal array is 0, then its ->first pointer will be NULL so the length can be counted instantly. For deferred arrays, this could get slow... but all of the current types of deferred arrays avoid creating an empty deferred array, and try hard to set the EDJ_ARRAY_LENGTH(array) to the proper value to avoid forcing a scan for edj_length().

Effects on edj_is_last()

The edj_is_last() function detects whether a given element is the last element; i.e. whether the next edj_next() will return NULL. Usually you don't need to know this, but every so often you do. For example, if you're generating a text form of the array and don't want an extra comma after the last element.

For non-deferred arrays this is easy. The last element is the one where ->next is NULL. For deferred arrays, that doesn't work but there are three other good techniques that do, and edj_is_last() knows them.

  1. Keep track of the index number for each element as it is returned by edj_first() or edj_next(). If it's one less than the array length, then that's the last one. This only works if the array length is known.
  2. One of the function pointers in edjdeffns_t is islast. Not all types of deferred arrays define that function, but if they do then that's the solution.
  3. Start a copy of the scan, and try edj_next() on the copy. If it returns NULL then the actual scan element is the last.

Honestly none of those three "good" ways are perfect though.

Nested Arrays

The JSON parser only considers deferring an array if it isn't nested inside another array. So for parsed data, an outer array may be deferred but any inner arrays will be entirely in memory.

Even so, it is possible to generate a edj_t tree that has nested deferred arrays. It's best to assume that any array could be nested unless you know exactly where the data comes from, and can trust it to only generate in-memory arrays.

The ... Operator

edj's ... operator returns a deferred array of integers between two numbers. It's just about the simplest case, so lets look at it in detail. It's implemented in the defer.c file.

The edj_defer_ellipsis() function creates the deferred array. It starts by calling the usual edj_array() to allocate an array; if the endpoint is smaller than the start, then it returns the empty array, no deferring needed.

Otherwise, though, it converts the empty array into a deferred array by allocating an instance of a private jell_t data type, which is a struct that starts with a edjdef_t. All fields are initialized as needed, including jell->basic->json->type = EDJ_DEFER, jell->basic->fns = &jell_fns, jell->from = from, and jell->to = to.

The jell_fns struct (which jell->basic->fns points to) contains function pointers to private jell_first() and jell_next() functions. Those functions return a edj_t for each successive integer, with the ->next pointing to a copy of the array's ->first.

It also defines ->islast() and ->byindex() functions. It does not define a function for doing extra freeing because none is needed; that's mostly for things like database access where you need to free the result set when you're done with it. It also does not define a function for searching by a key and value because integers aren't objects and hence have no keys.

Blobs

A blob is a binary object. They may be read from a binary file, or created via the blob() function.

In edj, the data is stored internally as a nice compact span of bytes, but you can access them as a deferred array. This allows you to access the data as an array of numbers, where each element corresponds to a single byte of data.

Parsing Large JSON Files

The JSON parser (in parse.c) detects large arrays, and makes them be deferred. When it encounters an array that isn't nested inside another array, and starts more than defersize bytes before the end of the file, then it calls a function named jskim() to parse the array without storing any elements; if the array's source text is at least defersize bytes long, then the array will be deferred.

Note that even the mere potential that an array could be deferred will cause it to be skimmed, and then either parsed immediately anyway (if small) or parsed piecemeal later (if deferred). Skimming + parsing is always slower than just parsing so deferred arrays will only save memory, not time. You should set defersize to a fairly large value to avoid this slowdown. The default value is 10000000 (ten million bytes of JSON text, which would typically consume about 50 megabytes of RAM if parsed) but you might want to increase that.

If the parser decides to defer the array, it will allocate jdefarray_t to store information about the location of the array within the JSON file. (The JSON files are mapped into memory, so this is simply a pair of pointers to the start and end of the array's source text. The file will remain mapped into memory as long as there's a deferred array continues to reference it.)

The jskim() function also counts the elements, and determines whether every element is an object (and hence whether the array is a table).

Deferred arrays from JSON files use ->first, ->next, and ->islast function pointers. They do not use ->free, ->byindex, or ->bykey.

Where Deferred Arrays Can't Happen

The edj_first()/edj_next() functions are used throughout edj, with one big exception: In the calcfunc.c file, which implements the built-in functions, arrays are used to store the function arguments. These are generated internally and are never deferred, so functions can use ->first and ->next safely. They often do a lot of validation of their arguments, so this is convenient. I've tried to mark most such instances (at least for ->next) with a /* non-deferred */ comment.

Another thing to consider is that objects also use linked lists to store their members, and they certainly aren't deferred arrays. You can still see many ->first/->next loops over object members in the library code. I've tried to mark them all with a /* object */ comment.
