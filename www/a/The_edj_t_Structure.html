The edj_t Data Type

2025-04-15

The edj_t data type is used to represent data parsed from a JSON document. It uses a tree structure. There are tree nodes representing the 6 basic data types. Most usage is pretty simple, but there are a few quirks. Strictly speaking, you don't need to know this unless you're writing C code that uses the edj library, but even if you only use edj interactively with a few basic scripts, this information might still be interesting.

Introduction

The edj library, and any C program that uses it, will make extensive use of edj_t pointers. In this article, we'll discuss the contents of a edj_t, and how a tree of them is used to represent data parsed from a JSON document.

The edj_t structure is defined in <json.h> as follows: 

      typedef struct edj_s {
        struct edj_s *next;	/* next element of an array or object */
        struct edj_s *first;	/* contents of this object, array, or key */
        jsontype_t type : 4;	/* type of this edj_t node */
        unsigned    memslot:12; /* used for EDJ_DEBUG_MEMORY */
        char        text[14];	/* value of string, number, boolean; name of key */
      } edj_t;

The most important field is ->type. It identifies the JSON data type that this edj_t contains, and will be one of the following symbols: EDJ_BOOLEAN, EDJ_NULL, EDJ_STRING, EDJ_NUMBER, EDJ_ARRAY, EDJ_DEFER, EDJ_OBJECT, or EDJ_KEY.

The ->text field generally stores string values, and the ->first field points to embedded data. I'll explain the details of how they're used for each JSON data type later in this article. Spoiler: For long text, edj allocates a jumbo-sized edj_t so the ->text field is big enough.

The ->next field is used for representing array elements or object members as a linked list. That makes ->next an unusual field because it's not about this edj_t; it's about the outer edj_t that contains it. Each element of an array, for example, will have a pointer to the next element of the array. The array uses each element's ->next to implement the linked list that stores the array.

The ->memslot field is used to track memory usage if you compile your program with -DEDJ_DEBUG_MEMORY. You can ignore it; it takes care of itself. If you're curious though, it is usually the line number where the edj_t was allocated, or the negative of the line number where it was freed. The absolute value can be used as an index into a memory_tracker C array to obtain the file name and true line number. (The value in ->memeslot might not be the actual line number, if some other source file also allocated/freed an edj on the same line number.)

Null

A JSON null is represented by an edj_t with EDJ_NULL stored in its ->type field. The other fields aren't used.

Nulls with an error message

JavaScript has many symbols for handing special cases such as NaN for "not a number" where a number would normally be expected. Those symbols aren't valid in JSON though, so edj uses null for all errors. Since edj_t's ->text and ->first fields aren't used for a basic null, edj will sometimes store error text and location into those fields.

Boolean

A JSON boolean value is stored in an edj_t with EDJ_BOOLEAN stored in its ->type field. The ->text field will contain either "true" or "false". You can use json->text[0] == 't' to test whether a boolean edj_t is true or not (though the edj_is_true() function is preferred).

String

A JSON string value is stored in an edj_t with EDJ_STRING in its ->type field. If the string is too long to fit in ->text then edj will allocate extra space to extend the size of ->text.

Strings are always stored in UTF-8 coding, with C's traditional \0 terminator. Any backslash escapes such as \n or \u0533 are converted first to Unicode and then to UTF-8, so the string is what it is. No further processing of backslashes is needed.

Well, almost. Strings are allowed to contain a NUL character, but since \0 is used as the string terminator, NUL is represented as \uffff. (In UTF-8, that's represented by the three-byte sequence 0xef,0xbf,xbf.) Unicode reserves \uffff for programs to use internally for... whatever. edj uses it to represent NUL. So \uffff is always output as a NUL byte, and using the "\0" escape in a string will add 0xef,0xbf,0xbf to the string instead of 0x00.

The ->first field is unused.

ISO-8601 Dates, Times, DateTimes, and Periods

These are all stored as strings. As far as edj_t is concerned, there's no difference between an ISO-8601 string and any other string.

Number

A JSON number is stored in an edj_t that has EDJ_NUMBER stored in its ->type field.

Values parsed from a JSON document are stored as strings in the ->text field. They are not immediately converted to binary for two reasons.

First, conversion between binary and text formats is about the slowest thing you can do with a floating point number because the CPU has no magic opcode to do it in hardware. Most numbers in a JSON document will either be entirely ignored, or they'll just be copied to the output verbatim. Either way, converting is a waste of time.

Second, conversion looses precision. The value 0.01 can't be exactly represented in floating point. We can minimize the consequences of that by keeping numbers in text form... until we need to do math on them.

Binary numbers

Not all numbers used by edj are parsed from JSON documents though. Number literals in scripts, or the results of computation, will be stored in binary. Again, this is done for the sake of speed and precision.

To store a binary number in an edj_t, the first byte of the ->text field is set to '\0' so the text is effectively an empty string. The second byte (json->text[1]) is set to 'i' for integer values, or 'd' for double-precision floating point values. Two macros, EDJ_INT(json) and EDJ_DOUBLE(json), let you access the last 4 or 8 bytes of the ->text field as an int or double.

Arrays

Arrays are stored as linked lists. The head of the list is an edj_t with ->type=EDJ_ARRAY, and the ->first field points to the first element of the array. Each element's ->next field points to the next element; the last element's ->next field is NULL.

Except for deferred arrays, described below.

Optimizations

Since arrays don't use the ->text field, we can use part of it to store a pointer to the end of the array. This is desirable because it speeds up appending to an array a hell of a lot! If we had to scan the whole array to add the next element every time, then building an array would have complexity of O(n2), but with a tail pointer it's just O(n). And JSON data often contains large arrays, so this really means something.

There is an EDJ_END_POINTER(json) macro which lets you access the last 8 bytes of the json->text field as a pointer to the last element. The edj_append(array, elem) function uses this to append a new element without having to scan the whole array each time.

Arrays abuse the ->text field in two other ways. ->text[1] indicates whether the array is a table ('t' for table, 'n' for non-table, or '\0' for unknown). Bytes 2 through 5 of ->text store a 32-bit length count; if the count is 0 but the ->first pointer is non-NULL, then it is invalid. These allow the edj_is_table(array) and edj_length(array) functions to return values immediately, without having to scan the whole array.

The ->text field is 14 bytes long, and its offset within the edj_t is 18 bytes. This means we're using (abusing) all bytes of ->text, but the length is aligned on a 4-byte boundary and the end pointer is aligned on an 8-byte boundary.

Deferred Arrays

The edj library supports deferred arrays. Instead of loading the whole array into RAM, the parser just does a quick scan to find its end (so it can parse whatever comes after the array), count its length, and check whether it is a table (array of objects). For deferred arrays, the array->first->type will be EDJ_DEFER instead of a normal data type.

Technically, the ->first pointer points to a larger struct which begins with an edj_t. The rest of the struct contains whatever data the deferred array needs to do its thing. Some of this is standard — there's a place to store the name of the deferring strategy, and some function pointers to do common things like find the first or next member. Usually, some of it is dependent on the deferring strategy though. For example, a deferred array such as 1...1000000 would store the first and last integers somewhere in its struct.

When C code wants to scan an array, it normally does so by calling the edj_first(array) and edj_next(elem) functions. If the array is entirely in RAM, then these are basically the same as array->first and elem->next.

But for deferred arrays, those functions find and retrieve the information wherever it may be. That usually means re-parsing the big array, one element at a time, and then freeing that element before moving to the next one. This is actually slower than parsing the big table once, but it saves RAM so it can be worth doing because of that.

If, while stepping through an array (deferred or not), you decide to stop scanning it before the end (i.e., before edj_next(elem) returns NULL) then you must call edj_break(elem) so the library can free any resources that it was using to support the array scan. It's safe to call edj_break(elem) on non-deferred arrays too.

Deferred arrays aren't used only for large arrays from JSON documents. They can be produced by other sources. For example, the expression 1...1000000 does not immediately allocate a million edj_t structures to store the array; it returns a deferred array that can step through the whole range, one integer at a time.

Objects and Keys

Objects are basically arrays of members. Like arrays, their contents are stored in a linked list.

An edj_t containing EDJ_OBJECT in its ->type field represents the object as a whole, and its ->first field points to its first member.

Each member is an edj_t that has EDJ_KEY in its ->type field. The member's key (name) is stored in the ->text field, and the value is pointed to by the ->first field. The ->next field is used to implement the linked list.

Unlike arrays, objects are never deferred. This means you can always just use object->first and member->next to step through the members.

/* C code */ edj_t *obj = edj_parse_string("{\"a\":[1,2,3],\"e\":true,\"i\":4,\"o\":{\"z\":null\},\"u\":1.8}"); edj_t *mem; for (mem = obj->first; mem; mem = mem->next)

Classes

edj doesn't support class... yet. The expectation is that it will some day, and each object's class name will be stored in its ->text field.

It's important to note that objects from a JSON document are always generic objects. No Class.

Optimizations

While parsing objects from a JSON document, we use the same EDJ_END_POINTER(json) macro trick that we use with arrays.

We only do this while parsing JSON documents, not while updating objects via scripts; this is because updates need to scan the object to avoid adding duplicates. That isn't an issue when parsing a JSON document though.

Since objects parsed from a JSON document never have a class, they never use the ->text field to store a class name, leaving it free to store the EDJ_END_POINTER(json). Objects elsewhere don't use EDJ_END_POINTER(json) so ->text is available to store a class name. Hence, there is never a conflict there.

The members' EDJ_KEY edj_t's also have an optimization. When initially parsed, the key is stored in the ->text field unchanged... but the size of the allocated ->text field is twice what we need to store the key. Later, if a case-insensitive key search is ever performed on the object, the simplified version of the key is generated once and stored in the extra space.
