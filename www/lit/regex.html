Regular expressions

Regular expressions are a common way to describe complex text patterns. edj uses them with the LIKE operator, and the match(), matchAll(), replace(), split(), find() and grep() functions.

Regular expressions are enclosed in / (slash) characters, and may be followed by i and/or g flags. The / character is also used as the division operator, but context allows the parser to figure it out. Regular expressions are really only used after a ( or , character, or after the LIKE operator.

You can append flags to the regular expression to alter its interpretation. These appear after the closing / character. The available flags are:

i Makes the regular expression be case-insensitive; without it, comparisons and searches would be case-sensitive.
e Uses the POSIX "extended" syntax for the regular expression, instead of the normal "basic" syntax. Mostly this affects when you need to use backslash characters.
g Applies the expression globally instead of just finding the first match. This affects the replace() and match() functions, effectively turning them into replaceAll() and matchAll().

For a full description of the regular expression syntax, see the Linux manual (i.e., run "man 7 regex"). The highlights are:

  • Most characters match only themselves. This include letters, digits, and whitespace.
  • A ^ at the start of the regular expression means it can only match text at the start of the target string.
  • A $ at the end of the regular expression means it can only match text at the end of the target string.
  • The . character matches any single character.
  • [ ] encloses sets of characters. This will match a single character from the text string, if it's in the set. The brackets can contain single characters, or pairs separated by a hyphen for a range of characters. For example [a-zA-Z0-9] matches any single ASCII letter or digit. There are also named sets, which are maybe more readable and more importantly handle non-ASCII characters too. For example, [[:alpha:]] matches any letter, including non-ASCII letters.
  • The * character is a "closure operator", which means it affects how often the expression before it (often just a single character) may be repeated. For * it can be repeated zero or more times. One common example is .* which matches any text at all. (That means any character, repeated any number of times).
  • \+ is a closure operator that means the preceding expression should repeat 1 or more times.
  • \? is a closure operator that means the preceding expression should occur 0 or 1 times; i.e. that it is optional.
  • \( \) marks subexpressions. These affect closure operators like * and \+, allowing them to match multi-character expressions. Also, the replace() function can access the text that matched each subexpression and use it when constructing replacement text.
  • Normally edj uses POSIX "basic" regular expressions, but appending an "e" flag makes it use "extended" regular expression syntax. The main difference is that metacharacters that require a backslash for "basic" regular expressions do not require them for "extended" regular expressions.
Examples
/foo/ null This was correctly parsed as a regular expression, but regular expressions don't work by themselves; they must be part of a function call or operator invocation. So the result is null.
"food" like /foo/ true This returns true because "food" does contain f-o-o.
"food" like /^foo$/ false This returns false because the $ means the target string isn't allowed to have any text after the matching text, but "food" has a "d" after the matching text. No good.
Notes
  • Since edj deals strictly with JSON data, and regular expressions aren't a valid JSON data type, I had to get clever. Regular expressions are handled like null except they also have sort of a side-channel where the regular expression is stored. When evaluating an expression, if a regular expression is used where it is expected (the LIKE operator or replace() function, basically) then the regular expression is seen and used; in any other context, the regular expression is just null.
  • One consequence of the above is that regular expressions can't be stored in a var or const.
  • Another consequence is that user-defined functions can't take regular expressions as arguments. Only built-in functions can. I'm not happy about this, and may change my mind later about the "strictly JSON" rule.
